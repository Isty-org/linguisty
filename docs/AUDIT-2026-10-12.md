## A1 · P2 · Общий таймаут сообщения обрывает долгий batch через 35 секунд

**Место:** `src/shared/messaging.ts:49` (общий `COMMAND_TIMEOUT_MS` задан на строке 8). Путь вызова: `src/content/controller.ts:126`, `:596`, `:600`, `:607`. Собственный watchdog страницы находится на `:583` и `:631`; фон использует бюджет batch на `src/background/controller.ts:398`.

**Trigger:** один корректный ответ batch занимает больше 35 s, но укладывается в настроенный per-attempt или общий retry/recovery budget. Это относится к Codex с `requestTimeoutMs=120000`, к обычному API с увеличенным timeout, а также к восстановлению/повторам при стандартных 25 s. У всех этих вызовов production `runtimeSendMessage` вызывается без `timeoutMs`.

**Факт и impact:** transport завершает ожидание `REQUEST_TIMEOUT` на 35 s. Страница переводит узел в `failed`, удаляет job и игнорирует последующий валидный ответ. Watchdog 305 s не помогает: раньше срабатывает другой таймер. Background при этом не получает команду отмены от этого таймаута и может продолжать запрос/восстановление до своего deadline. Это ошибка локального кода, а не ограничение времени жизни Chrome worker.

**Выполненное воспроизведение:** загружены настоящие `createPageController` и `sendMessage`, подменён только `wxt/browser` на mock runtime. В JSDOM создан `<p>Bonjour</p>` на `https://example.org`, `requestTimeoutMs=120000`, `streaming=false`. Runtime оставил batch pending. Детерминированный реестр таймеров зафиксировал `[1000, 305000, 35000]`. Вызов callback 35000 и drain microtasks дал:

```text
status=error, discovered=1, translated=0, failed=1, inFlight=0
error.code=REQUEST_TIMEOUT; DOM="Bonjour"
после валидного позднего ответа "Hello": те же state и DOM
```

Контроллер disposed, JSDOM закрыт; реального ожидания и сетевого inference не было. Отдельный direct `sendMessage(TRANSLATE_BATCH)` воспроизвёл такой же 35000 ms таймер и игнорирование позднего ответа.

**Scope исправления:** согласовать deadline production content transport с `batchTimeoutMs(settings.requestTimeoutMs)` и запасом доставки, включая каждую часть длинного узла. Сохранить короткие ограничения UI-команд, не увеличивать все сообщения до пяти минут. Проверить те же непродолженные 35 s ожидания у `TEST_CONNECTION`/`LIST_MODELS`, когда их разрешённый timeout выше. Добавить интеграционный тест именно с настоящим `shared/messaging`, иначе mock `options.sendMessage` снова скроет расхождение. Acceptance: ответ на 40 s при разрешённом бюджете успешно применяется; превышение общего бюджета, cancel и поздний ответ по-прежнему безопасны.

**Канон:** `spec://modules/page/FEAT-002-page-translation#queue`, `spec://modules/platform/INFRA-001-extension#runtime`, `spec://common/PROP-002-quality#resources`.

## A2 · P2 · Две временные ошибки recovery блокируют дальнейшие page-команды

**Место:** `src/background/controller.ts:143–149`, особенно условие `if (recoveryAttempts < 2) recovery = undefined` на строке 148.

**Trigger:** initial snapshot restore и следующая попытка чтения/восстановления завершаются ошибкой; затем browser storage снова работает. Не нужны повреждённые настройки или постоянный отказ browser API.

**Факт и impact:** rejected Promise второй попытки остаётся в `recovery`. Все последующие `START_TRANSLATION`, `GET_TAB_STATE`, cancel/display/page messages возвращают тот же `INTERNAL_ERROR`, не обращаясь к уже доступному storage. Повторная загрузка popup и кнопка повтора не восстанавливают работу в том же background instance, хотя публичная ошибка помечена `retryable:true`. Нужен новый background lifetime; обещанное повторение по следующему запросу не выполняется.

**Выполненное воспроизведение:** настоящий `registerBackgroundController`, существующие `fakeBrowser('moz-extension')`/`fakeDependencies` из `tests/background/harness.ts`; `storage.session.get` отклоняет первые два вызова и возвращает `{}` с третьего. После отклонения `controller.ready` дважды вызван `GET_TAB_STATE` от собственного popup sender:

```text
первый GET_TAB_STATE: ok=false, INTERNAL_ERROR, retryable=true, storage reads=2
следующий GET_TAB_STATE при исправном storage: тот же отказ, storage reads=2
```

Третьего чтения нет. `controller.dispose()` завершился. Существующий тест `tests/background/controller.test.ts:73` проверяет только один отказ и успешную вторую попытку; этого недостаточно.

**Scope исправления:** освобождать failed recovery promise для следующего явного запроса, сохранив coalescing одновременно ожидающих запросов, bounded timeout и защиту от late restore. Не добавлять бесконечный автоматический retry-loop. Если нужен backoff, он должен иметь конечный срок и разрешать последующее восстановление. Acceptance: два отказа → исправное storage → следующий явный запрос успешен; параллельные callers не запускают отдельные restores; поздний результат отменённой попытки не заменяет актуальную сессию.

**Канон:** `spec://modules/platform/INFRA-001-extension#recovery`.

## A3 · P2 · Короткие фрагменты текста страницы сохраняются в постоянном журнале

**Место:** `src/providers/diagnostics.ts:26–33`. Запись проходит через `:56`, `src/providers/request.ts:207` и `src/storage/errorLog.ts:82`.

**Trigger:** API error message содержит часть переданного исходного текста, состоящую из слов/чисел короче восьми символов; полного original с точной пунктуацией в сообщении нет. Например, узел `Tenant John Smith owes 250 EUR.`, ошибка `Invalid field: John Smith`.

**Факт и impact:** фильтр ищет весь original либо отдельные последовательности из >=8 букв/цифр (CJK >=4). Указанное имя проходит без редактирования. Даже `Tenant John Smith owes 250 EUR` без последней точки проходит целиком. В результате фрагмент содержимого страницы оказывается в `browser.storage.local` журнале с TTL до семи дней и в UI/копировании журнала. Это подтверждённое нежелательное локальное сохранение, **не установленная передача третьей стороне или утечка API-ключа**.

**Выполненное воспроизведение:** настоящий `OpenAICompatibleProvider` из registry получил mock HTTP400 JSON с указанным error message; `onError` вызвал настоящий `ErrorJournal.append`. StorageArea заменён in-memory объектом. После завершения запроса там присутствовала запись:

```json
{"linguisty.apiErrors":[{"operation":"translate","providerId":"openai-compatible","source":"api","model":"mock","errorCode":"INVALID_SETTINGS","attempts":1,"httpStatus":400,"apiCode":"invalid_request_error","message":"Invalid field: John Smith"}]}
```

Здесь опущены только автоматически созданные `id`/`createdAt`. Весь текст и ключ были синтетическими; пользовательские данные не читались. Direct `diagnosticText` отдельно подтвердил обе формы echo. Нынешний тест partial fragments использует длинное слитное `PrivateListing`, поэтому не покрывает эту границу.

**Scope исправления:** консервативно подавлять сообщения с такими фрагментами до сохранения; применить одинаковую защиту к `message`, `providerMessage`, request ID и другим свободным полям. Нельзя исправлять только UI или подменять исходную API-ошибку. Добавить end-to-end provider→journal регрессию с короткими именами, числовыми фрагментами и изменённой пунктуацией. Если произвольное error prose нельзя надёжно очистить, безопасная фиксированная замена предпочтительнее сохранения совпавшего содержимого; точные HTTP/code/type и публичный результат должны остаться полезными. Не заявлять защиту от всех возможных семантических пересказов по одному regex-тесту.

**Канон:** `spec://modules/translation/FEAT-001-engine#errors` (сообщение с фрагментами запроса скрывается целиком), `spec://modules/storage/INFRA-002-local-data#contracts`.

### Повторение repro без записи тестового файла

Исполнителю достаточно настоящих модулей и стандартного mock/fake-timer harness; зафиксированные выше inputs/outputs являются acceptance regression seeds. Для быстрого Node reproduction использовался следующий loader через PowerShell here-string в `node --input-type=commonjs`:

```js
const fs = require('node:fs'), Module = require('node:module');
const ts = require('typescript'), originalLoad = Module._load;
const browser = { runtime: { sendMessage: async () => ({ ok: true }) } };
Module._load = function (id, parent, main) {
  if (id === 'wxt/browser') return { browser };
  if (id === 'vitest') return { vi: { fn: f => f } }; // only existing fakeBrowser helpers
  return originalLoad.call(this, id, parent, main);
};
Module._extensions['.ts'] = (m, file) => m._compile(ts.transpileModule(
  fs.readFileSync(file, 'utf8'), { compilerOptions: {
    module: ts.ModuleKind.CommonJS, target: ts.ScriptTarget.ES2022,
  } }).outputText, file);
```

После loader A2 воспроизводится без fake timers:

```js
(async () => {
  const { registerBackgroundController } = require('./src/background/controller.ts');
  const { fakeBrowser, fakeDependencies } = require('./tests/background/harness.ts');
  const fake = fakeBrowser('moz-extension'); let reads = 0;
  fake.storage.get = async () => {
    if (++reads <= 2) throw new Error('synthetic transient error');
    return {};
  };
  const controller = registerBackgroundController({ api: fake.api, ...fakeDependencies().dependencies });
  await controller.ready.catch(() => {});
  const message = { channel: 'linguisty', type: 'GET_TAB_STATE', tabId: 1 };
  console.log(await controller.handleMessage(message, fake.ui), reads);
  console.log(await controller.handleMessage(message, fake.ui), reads);
  await controller.dispose();
})();
```

Минимальный A3: `require('./src/providers/diagnostics.ts').diagnosticText('Invalid field: John Smith', {texts:['Tenant John Smith owes 250 EUR.']})` возвращает исходную строку. Полный provider→journal путь также выполнен, как описано в A3. Для A1 подменяется только `browser.runtime.sendMessage`: batch promise остаётся pending, вызывается зарегистрированный callback 35000 ms, затем promise разрешается корректным результатом; production content controller сохраняет failed state.

### Уточнение браузерной границы A1 — 2026-10-13

По дополнительной диагностике координатора, Firefox получил loopback request примерно за 41 ms, затем соединение закрылось примерно через 30.15 s до получения headers; страница получила INTERNAL_ERROR. Это не повтор первоначального локального 35-секундного deadline A1. Обрыв на 30 s сам по себе ещё не устанавливает, кто закрыл ожидание. Исполнитель проверяет отдельный вариант с ранними headers/телом через 40 s и наблюдает background lifecycle без диагностических runtime messages, которые могли бы изменить его.

Официальные источники имеют разную применимость:

- [Chrome service worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle) прямо перечисляет ожидание fetch response более 30 s среди условий остановки **extension service worker Chrome**, отдельно от idle 30 s и обработки события 5 min. Эта документация относится к Chrome-сборке Linguisty с background.service_worker. Она не устанавливает причину наблюдавшегося Firefox FAIL. Прошедший Chrome тест подменял worker fetch и возвращал синтетический Response после задержки, поэтому не проверяет реальное сетевое ожидание headers более 30 s.
- [MDN background manifest](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background) описывает Firefox background.scripts/event page вместо поддерживаемого Chrome service worker. Это совпадает с manifest Linguisty. В [Mozilla ext-backgroundPage.js](https://github.com/mozilla-firefox/firefox/blob/main/toolkit/components/extensions/parent/ext-backgroundPage.js) текущей ветки main `extensions.background.idle.timeout` имеет default 30000 ms; есть reset/условия продления, включая pending listeners. Это **idle lifecycle**, не всеобщая гарантия «Firefox fetch всегда обрывается на 30 s»; main также не доказывает точное содержимое установленной версии 157.0.1.
- [Mozilla bug 1851373](https://bugzilla.mozilla.org/show_bug.cgi?id=1851373) касается исправленной регрессии Firefox 117 в reset idle через messaging. Он подтверждает значимость lifecycle для долгой работы, но не является доказательством того же бага в Firefox 157.0.1. Предложение [WECG runtime.waitUntil #416](https://github.com/w3c/webextensions/issues/416) всё ещё описывает предлагаемый механизм; считать его доступным production API на основании этого документа нельзя.

Было → стало в аудите: общая неопределённость Firefox long-batch уточнена до наблюдаемого обрыва до headers около 30 s и отдельной проверяемой lifecycle-гипотезы. ### Review RequestActivity и интеграции

Было → стало: допустимый Firefox batch терял фон около 30 s → один `RequestActivity` на background controller поддерживает активность только пока существуют ограниченные запросы. В `src/background/controller.ts:143` activeRequest передаёт helper именно результат abortable с deadline. Два места использования — TRANSLATE_BATCH (`:396`) и TEST_CONNECTION/LIST_MODELS (`:469`); batch ограничен максимум 300 s, provider UI request — максимум 120 s. Одного обещания bounded в комментарии недостаточно: эти реальные call sites проверены.

В `src/background/requestActivity.ts` параллельные работы разделяют один 20 s timer, число регистраций ограничено существующим MAX_API_REQUESTS controller; duplicate batch возвращает существующий Promise до создания новой активности. Пока getPlatformInfo pending, следующий вызов не запускается. Нет вызовов для коротких работ, завершившихся до первого тика, или при отсутствии запросов. Ответ getPlatformInfo не сохраняется; payload, ключи, storage, ports и новые permissions helper не использует. Синхронный throw и rejected activity API обработаны без подмены результата перевода.

Abort снимает регистрацию/свой listener синхронно, settlement делает это в finally; последняя регистрация очищает timer. Dispose controller сначала вызывает requestActivity.dispose (`:650`), до асинхронного storage cleanup. Даже provider Promise, игнорирующий abort, не оставляет активность после общего deadline. Поздний результат activity API только меняет pending flag и не создаёт новый timer. Отдельное ограничение: underlying browser API Promise физически не отменяется; если сам getPlatformInfo бесконечно зависнет, helper не обещает работоспособность повреждённого browser API. Проверено отсутствие накопления вызовов и принадлежащих helper timers/listeners, а не принудительная отмена внутренностей браузера.

Механизм для конечной долгой операции соответствует [Chrome migration guide](https://developer.chrome.com/docs/extensions/develop/migrate/to-service-workers#keep_a_service_worker_alive): периодический trivial API очищается после операции. Для Firefox просмотрена [parent implementation getPlatformInfo](https://github.com/mozilla-firefox/firefox/blob/main/toolkit/components/extensions/parent/ext-runtime.js); применимость к установленному Firefox подтверждает именно runtime regression ниже, а не перенос правил Chrome. Дополнительный поиск Stack Overflow/Reddit проведён до review; форумные советы не использованы как замена фактическим тестам.

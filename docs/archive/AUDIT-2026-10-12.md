## A1 · P2 · Shared message timeout interrupts a long batch after 35 seconds

**Location:** `src/shared/messaging.ts:49` (the shared `COMMAND_TIMEOUT_MS` is defined on line 8). Call path: `src/content/controller.ts:126`, `:596`, `:600`, `:607`. The page's own watchdog is at `:583` and `:631`; the background uses the batch budget at `src/background/controller.ts:398`.

**Trigger:** one valid batch response takes more than 35 s but stays within the configured per-attempt or total retry/recovery budget. This applies to Codex with `requestTimeoutMs=120000`, a regular API with an increased timeout, and recovery/retries at the standard 25 s. In all these calls, production `runtimeSendMessage` is called without `timeoutMs`.

**Fact and impact:** transport ends the wait with `REQUEST_TIMEOUT` at 35 s. The page marks the node `failed`, removes the job, and ignores a subsequent valid response. The 305 s watchdog does not help: another timer fires first. The background receives no cancellation command from this timeout and may continue requesting/recovering until its own deadline. This is a local-code error, not a Chrome worker lifetime limitation.

**Reproduction performed:** loaded the real `createPageController` and `sendMessage`, replacing only `wxt/browser` with a mock runtime. Created `<p>Bonjour</p>` in JSDOM at `https://example.org`, `requestTimeoutMs=120000`, `streaming=false`. Runtime left the batch pending. A deterministic timer registry recorded `[1000, 305000, 35000]`. Invoking callback 35000 and draining microtasks produced:

```text
status=error, discovered=1, translated=0, failed=1, inFlight=0
error.code=REQUEST_TIMEOUT; DOM="Bonjour"
after a valid late response "Hello": same state and DOM
```

The controller was disposed and JSDOM closed; no real wait or network inference occurred. A separate direct `sendMessage(TRANSLATE_BATCH)` reproduced the same 35000 ms timer and ignored late response.

**Fix scope:** align the production content transport deadline with `batchTimeoutMs(settings.requestTimeoutMs)` plus delivery allowance, including every part of a long node. Preserve short UI-command limits rather than increasing all messages to five minutes. Check the same unextended 35 s waits for `TEST_CONNECTION`/`LIST_MODELS` when their permitted timeout is higher. Add an integration test using the real `shared/messaging`; otherwise mock `options.sendMessage` will hide the discrepancy again. Acceptance: a response at 40 s is applied successfully within the allowed budget; total-budget overrun, cancellation, and late responses remain safe.

**Canonical specs:** `spec://modules/page/FEAT-002-page-translation#queue`, `spec://modules/platform/INFRA-001-extension#runtime`, `spec://common/PROP-002-quality#resources`.

## A2 · P2 · Two transient recovery failures block further page commands

**Location:** `src/background/controller.ts:143–149`, especially `if (recoveryAttempts < 2) recovery = undefined` on line 148.

**Trigger:** initial snapshot restore and the next read/restore attempt fail; browser storage then works again. Neither corrupted settings nor permanent browser API failure is needed.

**Fact and impact:** the second attempt's rejected Promise remains in `recovery`. All subsequent `START_TRANSLATION`, `GET_TAB_STATE`, cancel/display/page messages return the same `INTERNAL_ERROR` without accessing storage that is already available again. Reloading the popup and the retry button do not restore operation in the same background instance, although the public error is marked `retryable:true`. A new background lifetime is needed; the promised retry on the next request does not occur.

**Reproduction performed:** real `registerBackgroundController`, existing `fakeBrowser('moz-extension')`/`fakeDependencies` from `tests/background/harness.ts`; `storage.session.get` rejects the first two calls and returns `{}` from the third onward. After `controller.ready` rejected, `GET_TAB_STATE` was called twice from the extension's own popup sender:

```text
first GET_TAB_STATE: ok=false, INTERNAL_ERROR, retryable=true, storage reads=2
next GET_TAB_STATE with working storage: same failure, storage reads=2
```

There is no third read. `controller.dispose()` completed. The existing test at `tests/background/controller.test.ts:73` checks only one failure and a successful second attempt; that is insufficient.

**Fix scope:** release the failed recovery promise for the next explicit request, preserving coalescing of concurrent waiting requests, bounded timeout, and protection against late restore. Do not add an infinite automatic retry loop. If backoff is needed, it must have a finite duration and permit subsequent recovery. Acceptance: two failures → working storage → next explicit request succeeds; parallel callers do not launch separate restores; a late result from a canceled attempt does not replace the current session.

**Canonical spec:** `spec://modules/platform/INFRA-001-extension#recovery`.

## A3 · P2 · Short page-text fragments are saved in the persistent log

**Location:** `src/providers/diagnostics.ts:26–33`. Writing passes through `:56`, `src/providers/request.ts:207`, and `src/storage/errorLog.ts:82`.

**Trigger:** an API error message contains part of the transmitted source text consisting of words/numbers shorter than eight characters; the message does not contain the complete original with exact punctuation. For example, node `Tenant John Smith owes 250 EUR.`, error `Invalid field: John Smith`.

**Fact and impact:** the filter looks for the entire original or individual sequences of >=8 letters/digits (CJK >=4). That name passes without redaction. Even `Tenant John Smith owes 250 EUR` without the final period passes in full. As a result, a page-content fragment reaches the `browser.storage.local` log with a TTL of up to seven days and the log UI/copy output. This is confirmed unwanted local retention, **not established transmission to a third party or an API-key leak**.

**Reproduction performed:** the real `OpenAICompatibleProvider` from the registry received mock HTTP400 JSON with that error message; `onError` called the real `ErrorJournal.append`. StorageArea was replaced with an in-memory object. After the request completed, it contained this entry:

```json
{"linguisty.apiErrors":[{"operation":"translate","providerId":"openai-compatible","source":"api","model":"mock","errorCode":"INVALID_SETTINGS","attempts":1,"httpStatus":400,"apiCode":"invalid_request_error","message":"Invalid field: John Smith"}]}
```

Only automatically generated `id`/`createdAt` are omitted here. All text and the key were synthetic; user data was not read. Direct `diagnosticText` separately confirmed both echo forms. The current partial-fragments test uses the long joined `PrivateListing`, so it does not cover this boundary.

**Fix scope:** conservatively suppress messages containing such fragments before saving; apply the same protection to `message`, `providerMessage`, request ID, and other free-form fields. Fixing only the UI or replacing the original API error is insufficient. Add an end-to-end provider→journal regression with short names, numeric fragments, and changed punctuation. If arbitrary error prose cannot be sanitized reliably, a safe fixed replacement is preferable to retaining matched content; exact HTTP/code/type and the public result must remain useful. Do not claim protection against every possible semantic paraphrase from one regex test.

**Canonical specs:** `spec://modules/translation/FEAT-001-engine#errors` (a message containing request fragments is hidden entirely), `spec://modules/storage/INFRA-002-local-data#contracts`.

### A1: aligned deadline and release of waits

Before → after: default content transport used the shared 35 000 ms limit → `src/content/controller.ts:599` passes its own `batchTimeoutMs(requestTimeoutMs) + 5 000` and AbortSignal for each regular batch and each part of a long node. `src/shared/messaging.ts:14` caps the explicit timeout at 305 000 ms; short reads remain 5 s. TEST_CONNECTION/LIST_MODELS with settings receive a budget accounting for requestTimeoutMs. This fixes the transport/watchdog mismatch, not just the injected test transport.

`tests/content/batch-transport.test.ts` replaces only `wxt/browser` and uses real createPageController/sendMessage: a response at 40 s completes translation, long-node parts assemble, a stalled batch is bounded, cancel/original/dispose clear waits and reject late results. Tests check no timers remain after teardown. Additionally, a separate Node reproduction loaded the real TS shared helper in memory, left the runtime promise pending, invoked abort, then a late resolve: result CANCELLED, abort listener added/removed **1/1**, process exited without a retaining timer.

At settle and clearJobs, the job timer and controller are released; the transport handler clears the deadline/retry timer and listener. WebExtensions sendMessage itself gains no ability to physically cancel the underlying browser Promise: it may complete later, but the settled guard excludes a second commit. This is an API limitation, not a claim of complete release of all browser-internal memory.

Both existing manifests show 0.4.8. The reviewed Chrome and Firefox `translate.js` are identical byte for byte: SHA-256 `506b033f03e1f82ea15c14b8eb315262e897b6f3453cd5ee5060e3463b43fea4`, containing the 305 000 ms limit. This is a limited check of built content, not proof of Firefox scenario success or an independent comparison of every ZIP. According to the coordinator's latest message, Firefox retained Bonjour after 90 s; the WI-033 assignee is diagnosing harness/production. A1's browser verdict remains open.

### A2: retry after failure, coalescing, late reads

Before → after: recovery stayed rejected forever after two failures → `src/background/controller.ts:141` retains only the current attempt, and the rejection handler resets that exact attempt if still current. The next request initiates a new bounded attempt; concurrent requests share one Promise. Successful recovery is retained; there is no infinite automatic retry loop.

Four focused tests confirmed: settings available after failure; after two failures, two concurrent GET_TAB_STATE perform one third read and receive a restored session; timeout of the old restore does not prevent a new attempt, and a late old response does not write a snapshot or resurrect a session; dispose cancels retry and leaves commands/messages/sessions and timers at zero. Tab closure after a successful retry preserves an empty snapshot: cleanupTab now uses `(recovery ?? ready)` on line 567. Dispose awaits the current recovery on line 649.

Separately repeated the original minimal reproduction without Vitest behavioral mocks: storage.get throws the first two times and returns `{}` from the third onward. Result: second read — retryable error, next GET_TAB_STATE — success, reads=3. Controller disposed. Physical cancellation of an already started browser.storage.set was not checked in this pass; the late-read guard must not be presented as that guarantee.

### RequestActivity and integration review

Before → after: an allowed Firefox batch lost its background near 30 s → one `RequestActivity` per background controller maintains activity only while bounded requests exist. In `src/background/controller.ts:143`, activeRequest passes the helper the result of abortable with a deadline. Two call sites are TRANSLATE_BATCH (`:396`) and TEST_CONNECTION/LIST_MODELS (`:469`); the batch is bounded to at most 300 s, the provider UI request to at most 120 s. A comment promising bounded operation is insufficient: these actual call sites were reviewed.

In `src/background/requestActivity.ts`, parallel operations share one 20 s timer, registration count is bounded by the controller's existing MAX_API_REQUESTS; a duplicate batch returns the existing Promise before creating new activity. While getPlatformInfo is pending, another call is not launched. There are no calls for short operations completed before the first tick or when no requests exist. The getPlatformInfo response is not retained; the helper uses no payload, keys, storage, ports, or new permissions. Synchronous throws and a rejected activity API are handled without replacing the translation result.

Abort removes the registration/owned listener synchronously; settlement does so in finally; the last registration clears the timer. Controller dispose first calls requestActivity.dispose (`:650`), before asynchronous storage cleanup. Even a provider Promise ignoring abort does not leave activity beyond the overall deadline. A late activity-API result only changes the pending flag and creates no new timer. Separate limitation: the underlying browser API Promise is not physically canceled; if getPlatformInfo itself stalls forever, the helper does not promise a malfunctioning browser API will work. Checked: no accumulation of calls or helper-owned timers/listeners, not forced cancellation of browser internals.

The mechanism for a finite long operation follows the [Chrome migration guide](https://developer.chrome.com/docs/extensions/develop/migrate/to-service-workers#keep_a_service_worker_alive): periodic trivial API activity is cleared after the operation. For Firefox, the [parent getPlatformInfo implementation](https://github.com/mozilla-firefox/firefox/blob/main/toolkit/components/extensions/parent/ext-runtime.js) was reviewed; applicability to installed Firefox is confirmed by the runtime regression below, not by transferring Chrome rules.
